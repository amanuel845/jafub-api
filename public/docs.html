GitHub API Playground

A compact, interactive GitHub REST + GraphQL explorer designed to run as a Vercel serverless application. Test authenticated and public GitHub API operations without exposing direct browser-to-GitHub routing.

RESTGraphQLVercelNode 20Fine-grained PATRate telemetryMobile responsive

Quick start

  1. Create a new GitHub repository and upload the project.
  2. Import the repository into Vercel.
  3. Deploy using the included Node 20 configuration.
  4. Open the playground and optionally select Auth to enter a GitHub fine-grained personal access token.
  5. Select an endpoint or type a custom path, then press Send.
Local development: install dependencies, then run npm run dev with the Vercel CLI.

Features

REST Explorer

GET, POST, PUT, PATCH and DELETE against arbitrary GitHub REST paths.

GraphQL Explorer

Run GraphQL queries with JSON variables and inspect responses.

Authentication

Fine-grained PAT entry with browser-side persistence and clear controls.

Rate & Usage

Shows observed limit, remaining, used and resource values from GitHub headers.

Request History

Recent request method, path, status and latency are retained for the current session.

Developer tools

JSON formatting, raw/pretty responses, copy actions and cURL generation.

Endpoint catalog

Core, repositories, issues/PRs, search, organizations, Actions, gists, Git data, packages and security.

Custom paths

The REST path field can call endpoints that are not included in the preset catalog.

Mobile UI

Compact tabs and responsive layouts for phone and desktop browsers.

Architecture

The application uses a browser frontend and Vercel serverless proxy functions:

Browser
  │
  ├── /api/github/<path> ──► GitHub REST API
  │
  └── /api/graphql ─────────► GitHub GraphQL API
          │
          ▼
      GitHub response
          │
          ▼
     Playground UI

The proxy is responsible for forwarding authentication and GitHub API headers while allowing the frontend to use same-origin /api/… routes.

REST proxy

The REST proxy uses the Vercel catch-all route api/github/[...path].js. A request such as:

GET /api/github/repos/OWNER/REPO/issues?state=open

is forwarded to:

GET https://api.github.com/repos/OWNER/REPO/issues?state=open
HTTP methodSupportedTypical use
GET✓Read, list and search resources.
POST✓Create resources or trigger actions.
PUT✓Replace/update operations requiring PUT.
PATCH✓Partial resource updates.
DELETE✓Delete supported resources.

Request body

For POST, PUT and PATCH, enter JSON in the request editor. The playground validates/serializes JSON before sending it through the proxy.

Custom paths

The path box accepts any GitHub REST path beginning with /. Query strings are preserved, so endpoints outside the visible catalog remain testable.

GraphQL

The GraphQL proxy is POST /api/graphql. It accepts a query, variables object and optional operation name.

{
  "query": "query Viewer { viewer { login name } }",
  "variables": {},
  "operationName": "Viewer"
}

The request is forwarded to https://api.github.com/graphql. The playground displays the returned GraphQL JSON and HTTP status/latency.

Rate limits & usage

The Rate & Usage tab displays values observed directly from GitHub response headers. It does not invent a universal quota number because GitHub can expose different limits for different resource buckets and authentication states.

Important: the session request counter is a playground metric. It is not the same thing as GitHub's remaining quota.

Authentication

The playground supports a GitHub fine-grained personal access token (PAT). When saved, the browser sends it as:

Authorization: Bearer github_pat_…

Use a token with only the repository/account permissions required for the operations you are testing.

Public vs authenticated requests

Without a token, requests use GitHub's public/unauthenticated access rules. With a token, GitHub evaluates the token's permissions and authenticated rate limits.

Security

Browser storage warning: the playground stores the entered PAT in localStorage for convenience. Any JavaScript running in the same origin can potentially access localStorage. This is suitable for a personal developer playground, not a hardened secret-management system.
  • Never commit a PAT to GitHub.
  • Use the minimum token permissions required.
  • Set an appropriate token expiration.
  • Clear the token from the Auth dialog when finished.
  • For a public-facing deployment, consider adding application authentication and restrictive CORS.
  • For stronger secret handling, move credentials to Vercel environment variables and keep privileged calls server-side.

Vercel deployment

  1. Create a new GitHub repository.
  2. Upload/push the playground files.
  3. Import the repository into Vercel.
  4. Use Node 20.x.
  5. Deploy. No separate frontend build step is required because the UI is static HTML.

Configuration

The included project targets Node 20.x. The REST function is configured for a longer serverless execution window than the metadata helper, while the frontend remains a static HTML application.

{
  "version": 2,
  "functions": {
    "api/github/[...path].js": {
      "maxDuration": 60,
      "memory": 512
    },
    "api/graphql.js": {
      "maxDuration": 60,
      "memory": 512
    }
  }
}

The application does not require a build framework; Vercel serves the static frontend and executes the files under api/ as serverless functions.
